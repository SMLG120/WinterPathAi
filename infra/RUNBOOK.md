# WinterPath runbook — local ops, backup, rollback

No step here deploys or creates cloud resources. Production deploys are separate and
require explicit user approval.

## 1. Local stack
```bash
make up-db        # PostGIS only (shared container `winterpath-db-1`, 127.0.0.1:55432)
make up           # + api/web if services/api and apps/web exist on this branch (else SKIP message)
make down         # stop containers; the shared volume winterpath_pgdata is kept
make test         # integration tests (stub unless API_BASE_URL is set) + package tests
make contract     # Schemathesis only
make lint         # ruff, web lint, actionlint, shellcheck, compose config
make secrets      # gitleaks over full history
make audit        # pip-audit + npm audit (high)
```
Credentials: `.env.local` (untracked, generated by `scripts/create-worktrees.sh`). Every agent
worktree shares one container because the compose project name is pinned to `winterpath`.
**`make down` from any worktree stops the DB for all agents** — announce before running it.

Databases: `wp_data wp_routing wp_ml wp_platform wp_integration`, each with `postgis`.
Group roles: `wp_reader`, `wp_writer` (⊃ reader), `wp_migrator` (may create schemas).
If the volume pre-dates a bootstrap change: `infra/scripts/db-bootstrap.sh` (idempotent).

### Wiping the local DB (destructive — local dev data only)
```bash
docker compose --env-file .env.local down -v   # deletes winterpath_pgdata for ALL agents
```
Ask the other agents/coordinator first.

## 2. Health checks
- DB: `docker compose --env-file .env.local ps db` → `healthy`.
- API: `curl -fsS http://127.0.0.1:8105/api/v1/health` → `status` in `ok|degraded`
  (semantics in `infra/OBSERVABILITY.md` §2).

## 3. Backup
Local:
```bash
infra/scripts/db-backup.sh wp_integration            # -> ../winterpath-backups/<db>_<UTC>.dump + .sha256
```
Backups are written **outside the repository** (never commit dumps). Before any migration in a
shared environment: take a dump, record its SHA-256 in the change log, and verify it restores
into a scratch DB (`db-restore.sh <dump> wp_restore_check`).

Hosted (Supabase, once approved): use the plan's managed backups (verify retention) **and** a
logical `pg_dump -Fc` run by the operator with the `wp_migrate` login before each migration.

## 4. Restore
```bash
infra/scripts/db-restore.sh ../winterpath-backups/wp_integration_<ts>.dump wp_integration_restored
```
The script verifies the checksum, refuses to overwrite an existing database, and restores into
a new one. Point the service at it (`DATABASE_URL`) after verifying row counts and `/health`.

## 5. Rollback
| What | How | Notes |
|---|---|---|
| API (Render, once approved) | Render dashboard → service → Deploys → "Rollback" to previous deploy; `autoDeploy` is off | Image is immutable per commit; rollback does not touch the DB |
| Web (Vercel, once approved) | Vercel → Deployments → previous → "Promote to Production" (instant rollback) | Static only; check API compatibility (contract version) |
| DB migration | Prefer forward-fix. If required: `alembic downgrade <rev>` with `wp_migrator` **only if** the migration's downgrade is tested; else restore the pre-migration dump into a new DB and repoint | Data agent owns migrations; every migration must ship a tested downgrade or be marked irreversible |
| Ingestion run | Failed runs never replace current data (staging + swap, data-model.md). Re-run previous successful `ingest_run_id` inputs if a bad run was swapped in | |
| Model artifact | Revert `models/registry.json` active entry to the previous artifact; `/models/status` must reflect it | ML agent owns registry |

Rollback order when a release spans layers: web → API → DB (reverse of deploy order
DB → API → web). Never force-push to undo a release; revert commits.

## 6. Incident checklist
1. Check `/health` and recent `level=error` log lines (by `request_id`).
2. If a data source is wrong/unsafe, set it `disabled` (source registry) rather than serving
   stale data silently — the UI shows `unknown`, never "safe".
3. If precise coordinates or personal data appear in logs: stop log shipping, purge the
   affected log range, record the incident (Law 25 confidentiality-incident register — needs
   counsel review), fix and add a regression case to `tests/integration/test_privacy.py`.
4. If a secret is committed: rotate it first, then remove from history only with coordinator
   approval (no force-push without the user's explicit authorization).
